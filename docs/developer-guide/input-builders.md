# Input Builders

Status: implementation contract for the reusable Input Builder capability.
This page owns builder registration, the declared role binding, the authoring
envelope, submission verification and Clone & Reuse restoration. It does not
own an editor's scientific semantics; those remain in the upstream provider.

An Input Builder is a browser-side scientific editor that produces one or more
declared Task input files. Core owns the boundary that makes that safe:

- which builder a Task may use, and which logical output binds to which input
  role (declared in the owning `task.yaml`);
- the bounded authoring envelope the browser submits, persisted with the Task;
- SHA-256 verification of the accepted immutable bytes;
- ownership, persistence, task identity, execution and Clone & Reuse.

Builders own only authoring and provider-native capture. Generated bytes are
the execution authority. A builder's native snapshot is never treated as proof
of scientific equivalence.

## Declaration

A Task declares the built-in `input-builder` capability:

```yaml
input_workspace:
  steps:
  - id: material
    title: Provide the molecular system
    capabilities:
    - plugin: files
      id: source_files
      title: AlphaFold 3 JSON input
    - plugin: input-builder
      id: bionuta_builder
      title: Build with BioNuTA
      options:
        builder: bionuta          # registered builder ID
        target: alphafold3        # one of the builder's declared targets
        outputs:
          input: specification    # logical output -> declared input role
        # exclusive: true         # self-contained output; no other input file
```

Rules enforced at contract load:

- the builder must be visible to this Task (a shared builder, or one
  contributed by the same runner family);
- the target must be declared by that builder;
- every logical output must map to an existing role, and the role must accept
  the target's serialized format (`json`, `yaml`, `fasta`, `cif`);
- only the logical output `input` exists today;
- two builder capabilities may not claim the same role.

`exclusive: true` means the builder output is the Task's only input (for
example an annotated CIF that replaces a separate scaffold). Core refuses a
submission that also carries another accepted file.

The `files` upload capability stays visible and usable on every migrated Task.
A plain JSON/YAML/CIF upload is always a first-class path.

## Registration

Shared builders are deployment-owned in `revocompute/input_builders.py`.
`bionuta` is the shared workbench. A runner family contributes a scoped builder
through `plugin.yaml`:

```yaml
contributions:
  input_builders:
  - id: atomworks
    api_version: 1
    builder_version: 1
    state_schema_version: 1
    targets:
      rfd4: cif
    adapter: atomworks
```

The client adapter is selected by `adapter`. `bionuta` and `atomworks` are the
shipped adapters. A new adapter is a thin frontend module, not a new host: it
must expose `materialize()`, `restore(state)`, `subscribe()` and `destroy()`.

Workspace payloads project each referenced builder with an operational
`available` flag. Availability is a fact from the deployment (staged assets or
configured service), never a manifest claim. When it is false the frontend
offers only ordinary upload.

## Authoring envelope

The capability's workspace value is a versioned envelope, persisted in the
Task's `input_form.workspace`:

```json
{
  "version": 1,
  "builder": "bionuta",
  "builder_version": 2,
  "state_schema_version": 1,
  "target": "alphafold3",
  "revision": 4,
  "state": { "...": "provider-native, opaque to Core" },
  "dependencies": [],
  "outputs": [
    {
      "logical": "input",
      "role": "specification",
      "name": "bionuta-alphafold3.json",
      "size": 1284,
      "sha256": "..."
    }
  ]
}
```

`revision` is the mounted editor's monotonic edit counter. It is metadata, not
Task identity. The native `state` is bounded to 512 KiB (the enclosing workspace
document is capped at 1 MiB); larger states are rejected explicitly.

### Submission verification

After uploads are quarantined and hashed, and before a Task ID is derived, the
Server verifies each submitted envelope against the accepted files:

- the envelope names this capability's builder and target;
- every declared logical output binds exactly one accepted file in its declared
  role with the same name, size and SHA-256;
- no unbound file sits in a builder-owned role;
- a non-empty dependency list is refused (`builder_dependency_unsupported`)
  because no current Task declares a role and Runner staging layout for those
  bytes. Export the generated file and upload it with its dependencies instead.

Preflight performs the same check. Generated bytes remain authoritative: the
Server recomputes the digest from the bytes it accepted.

Capture requires a valid editor snapshot. The frontend invalidates its own
output immediately on an editor change, never overwrites an independent upload,
and refuses to bind after the role is replaced while a capture is in flight.
An unavailable, slow or failed builder leaves the upload path usable.

## Clone & Reuse

A clone plan carries only bounded compatibility metadata per builder capability
(`authoring`): capability ID, builder, target, versions, revision, output
digests and availability. It never carries the native document, a session ID,
a path or a signed URL.

The native state is resolved per capability over the owner-scoped, expiring
authoring path:

```text
GET /compute/api/clone-plans/{plan_id}/authoring/{capability_id}
```

The source Task is re-read at that moment, so deletion, a visibility change or
a builder-version change is observed. The response is `private, no-store`.

The draft mounts the builder, restores the recorded native state, re-materializes
against the current declared roles, and binds the result through the ordinary
input path. It compares the new output digest with the source:

- unchanged bytes: the input is restored normally;
- different bytes: the draft keeps the current bytes and states both digests.
  It never describes the result as the same scientific input silently;
- unavailable, expired or incompatible state: an explicit error, with upload as
  the fallback.

Cloning never mutates the source, reserves resources or submits. Old Tasks with
no authoring state keep the manual-upload behavior.

## Deployment

### BioNuTA

The workbench is third-party Apache-2.0 code and is not committed. Stage the
pinned commit before starting the server:

```bash
python tools/fetch_bionuta_assets.py --destination "$SERVER_DIR/vendor/bionuta"
```

The tool downloads the exact commit archive, extracts only an explicit
allowlist of static files, and verifies `frontend/provenance/bionuta.json`
(`tree_sha256`, file count, bytes) before swapping the tree into place. It
never builds or executes anything from the archive.

- The server reads `<SERVER_DIR>/vendor/bionuta` (`REVOCOMPUTE_BIONUTA_ROOT`).
  The fetch tool stages into the checkout's `vendor/bionuta` by default, so a
  deployment must pass `--destination` as shown above.
- Served same-origin at `/compute/bionuta/<asset>` behind login.
- The response CSP permits only this origin for scripts, styles, frames and
  data (`connect-src 'self'`), so optional external UniProt/glycan lookups are
  unreachable by design. The editor is not a cross-origin message bridge.
- The embedding iframe is same-origin and is **not** a security sandbox. The
  shipped browser dependencies are part of the asset trust, audited at the
  pinned commit. Do not serve the upstream dev/build server.

Known limit: BioNuTA's SugarDrawer iframe loads `sugardrawer/dist/index.html`,
an upstream build artifact not present in the pinned source tree. Glycan
drawing therefore stays unavailable unless a deployment stages that built
directory itself. The rest of the workbench, including target serialization,
validation, snapshots and restore, works without it.

### AtomWorks Studio (optional)

Studio is a separate CPU-only FastAPI service. Pin it at the reviewed release
(`atomworks-studio 0.0.12`, which pins `atomworks[ml]==3.0.4`) and run one
process:

```bash
atomworks-studio --host 127.0.0.1 --port 8000
```

Configure `REVOCOMPUTE_ATOMWORKS_STUDIO_URL=http://127.0.0.1:8000`. Absent or
empty disables the builder; the RFD4 task keeps its YAML/JSON + scaffold path.
The shared guest account also sees it as unavailable: guests share one identity,
so per-user session ownership cannot separate them.

The server exposes a small owner-scoped gateway, not a blanket reverse proxy:

- `POST /api/sessions` records the created session against the caller;
- only the documented session subpaths, health/ready/schema, examples and
  import inspection are forwarded;
- a session ID owned by another user is answered exactly like a missing one and
  is never forwarded upstream;
- client cookies, authorization and forwarding headers are not sent to Studio;
- `/compute/atomworks/api/...` is refused: API traffic enters only through the
  owner-scoped `/api/...` gateway, never through the asset route;
- the editor shell and its assets are served under `/compute/atomworks/` so the
  editor's absolute `/api/...` calls stay on this origin and pass the ownership
  gate.

Studio keeps sessions in memory and expires them; a 404 from export is surfaced
as an expired session with recovery guidance. Durable state is the exported
annotated CIF, not a session ID. The editor's `changed` postMessage invalidates
the bound output; Apply is an explicit capture of the current snapshot.

No model weights, GPU allocation, Gradio generation queue, new scheduler or
editor fork is part of this integration. RFD4's `num_designs`, `steps` and
`seed` stay in the existing typed Task parameters. Studio's annotated CIF binds
to `condition` with `exclusive: true`, so it cannot be submitted together with a
scaffold; the existing YAML/JSON + scaffold path is unchanged.

## Limits

- Builder dependencies are refused in this delivery, not silently dropped.
- Opaque authoring state is capped at 512 KiB per capability, below the 1 MiB
  workspace document limit.
- Task identity is derived from the accepted bytes and typed parameters, not
  from editor state. Submitting the same bytes returns the existing Task and
  never overwrites its authoring record; a different authoring state that
  serializes to identical bytes is the same scientific input.
- Core's existing upload and decoded-byte limits apply unchanged; provider
  limits never raise them.
- A runner that is not deployed or ready still refuses submission through the
  ordinary admission path; Input Builders change no resource policy.
