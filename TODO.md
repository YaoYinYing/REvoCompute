# Input Builder integration — BioNuTA and AtomWorks Studio

Temporary delivery checklist for this PR. The objective is to integrate existing upstream editors, not implement another molecular editor. Deliver the smallest reusable Core abstraction that supports both a shared/public builder (BioNuTA) and a runner-scoped/private builder (AtomWorks Studio for RFD4). Public/private describe plugin scope, not data visibility or user permissions.

## 1. Architecture and responsibilities

- [ ] Extend the existing InputWorkspace/WorkspacePlugin mechanism; no replacement plugin registry, generic workflow engine, common molecular schema, or editor-specific fields in Core. Introduce a small, typed Input Builder capability/controller lifecycle for asynchronous mounting, readiness/changes, validation, revision-bound materialization, snapshot/restore and disposal. Prefer composition with current plugin lifecycle rather than breaking unrelated synchronous plugins.
- [ ] Shared builder registration is deployment-owned; runner-scoped builder registration uses existing verified contribution manifests/namespacing. Task manifests declare an approved builder ID, target/dialect and mapping of logical outputs to existing input roles. Validate unknown IDs, invalid targets/options, role/cardinality/mode mismatches and duplicate ownership at contract load or before use. Illustrative mapping: AF3/OpenDDE `specification`, BioEmu2 `system`, RFD4 `condition`. Do not accept arbitrary module/service URLs or credentials from user data. Match existing API/manifest conventions instead of copying example syntax uncritically.
- [ ] Define a minimal versioned generic envelope: stable capability instance ID, builder ID, builder/artifact revision, state schema version, target, bounded opaque provider state (or authorized blob refs), logical dependencies, materialized output role/name/size/digest binding. Keep per-mount token and monotonic edit revision separate from persistent scientific state. Provider owns its domain schema; Core owns contract, trust, authorization, limits, storage, input roles, task identity and execution. A logical output may be one or more declared input files, not an executable command.
- [ ] Preserve provider-native parameters inside their materialized input; runtime parameters stay in the existing typed Task schema. Avoid duplicate knobs or undocumented override precedence (especially OpenDDE seeds vs JSON and RFD4 generation settings). Validate actual Runner behavior and document effective precedence; do not change defaults or routing gratuitously.
- [ ] One UI strategy: within Create Task let the reader choose Build input or Upload file. Keep the original upload path functional when builder is unavailable, slow or disabled; no auto-submission; no new global editor page required. Existing tasks and legacy clients without a builder are unchanged.

## 2. Draft lifecycle, binding and trust boundary

- [ ] Build output directly into the ordinary role files/submission path without download/reupload interaction. Use explicit apply/generate or safe debounced change handling as appropriate; invalidate builder-owned output immediately on relevant edit. Track actual binding ownership per capability, role and mount/revision; uploads or other capabilities are never overwritten silently. Provide intentional replacement/switch UI and clear state. Prevent stale async completion, restore races, mixed revision bundles, double submit and writes after unmount. Async preparation happens before review/preflight/submit capture, and preflight and final submit operate on the same authorized inputs; invalid/pending selected builder cannot submit stale output. Ordinary file-only mode must remain usable.
- [ ] Treat materialization and all provider output as untrusted, even if server-side. Reuse Core quarantine, role validation, size/count/MIME/format/cardinality checks, hashing and immutable publication. Preserve existing 16 MiB upload limits and any separate authorized-reference budgets unless explicitly approved; do not use provider limits to raise Core budget. No arbitrary filesystem paths, URLs, shell, symlinks, client-chosen storage keys, raw service response passthrough, or new bypass. Explicit safe unsupported-dependency diagnostics where Task/Runner has no suitable declared role and byte-staging semantics.
- [ ] Persist only the snapshot and dependencies actually associated with the accepted materialized role set. Server computes/verifies output and dependency digests and matches envelope to current registered capability/target/roles; reject mismatch, oversize, unknown/duplicate fields at envelope layer and missing data. Provider-specific state is opaque to Core except bounded structural/schema/version checks and provider validation where available. Never treat a client snapshot as attested scientific equivalence just because its digest matches a claimed output; generated bytes remain execution authority and restore must re-materialize and compare. No arbitrary state in logs, URLs, public results, telemetry or generated runner commands. Store authoring data under existing private ownership, lifecycle/accounting and cleanup.
- [ ] Preserve canonical calculation identity from resolved execution inputs and parameters; do not insert cosmetic/editor state indiscriminately into scientific task ID. Inspect actual dedup semantics: identical scientific input may have different editable states or submitters. Never overwrite an existing immutable snapshot or leak another owner's authoring state on dedup/retry. Use an owner-scoped immutable authoring receipt linked to exact accepted input digests if necessary; if current model cannot represent multiple states safely, define and test explicit conflict/retention behavior (do not claim the newer state was saved when it wasn't). Avoid general data-model rewrite. Legacy task.json and Runner-visible inputs remain backward compatible.
- [ ] Use existing transactional submission/snapshot mechanisms so failures leave no falsely committed state, orphan authoring blobs or jobs with missing inputs; include retry, concurrent submission, delete/expiry and rollback tests. Update OpenAPI and generated types atomically with API changes. Keep scientific Task parameters and editor provenance separate.

## 3. Clone & Reuse

- [ ] Extend existing read-only owner-scoped expiring clone plan and WorkspacePreset, rather than add a second clone system. Return only bounded compatibility metadata and authorized opaque references in plans; never raw scientific document, signed URLs, filesystem paths, live editor session IDs or file bytes in route/query. Resolve saved state/dependencies over a dedicated bounded authenticated clone-plan path using existing download/authorization primitives where suitable. Recheck owner entitlement, source visibility/deletion, current contract, exact recorded digests and reference expiry at read; never extend access merely because task results are visible/shared. Old tasks without authoring state stay on current manual input behavior.
- [ ] Restore compatible parameters and selected builder in a fresh draft exactly once; asynchronously stage state restoration, explicitly handle pending/failed restores and user edits; atomic replacement or leave current draft intact. Preserve independent roles such as BioEmu2 starting structure and RFD4 scaffold according to current authority and cardinality. Explicitly show missing/expired/unsupported data and allow manual fallback; no guessing, silent defaults or silent conversion. Apply clone only to an authorized new draft, never mutate source or automatically reserve/submit. Check Reset/Revert, demos, navigation, mode change, retry and source changes; no rollback that overwrites later edits.
- [ ] Reconstruct the editor from the saved native state and authorized dependency bytes; materialize against the current declared roles and verify accepted bytes/digests (byte identity when deterministic, provider-specific equivalence only when documented and tested). Display incompatibility or changed output as an actionable reconciliation, never describe it as the same scientific input silently. User can deliberately revise and create a different run. Pinned upstream/version compatibility policy explicit; no mandatory support for unreleased or incomplete drafts.
- [ ] Tests for successful clone/edit/resubmit, unchanged reconstruction, source remains immutable, unauthorized user with visible result, expired/deleted source, missing dependency, digest mismatch, unavailable builder, incompatible version/target, tampered state, duplicate inputs, unowned upload preservation, user edit races. Prove actual server persistence and retrieval, not only in-memory browser harness.

## Definition of done

One existing Create Task workspace supports reusable, declaratively registered Input Builders. BioNuTA and native AtomWorks Studio use thin adapters and do not duplicate scientific editors; accepted materialized input remains authoritative; authorized Clone & Reuse restores reconstructible native state and verified dependencies for enabled providers. Ordinary uploads and legacy tasks still function. Real integration evidence, security/compatibility limits, independent review/audit and final head are documented. No unrelated platform rewrite.
